一座数字花园不需要一开始就拥有所有功能。它需要一条清楚的路径：把想法写下来，让读者找到它，再让这些内容慢慢建立联系。这篇示例手记展示博客的正文排版和内容组织方式。

## 先确定内容的形状

文章的标题可以改，地址应该稳定。为每篇文章指定一个与标题独立的 `slug`，可以减少以后改名、调整栏目时的链接维护。

```yaml
slug: digital-garden
title: 从一篇文章开始，种一座数字花园
summary: 从内容出发，构建一个适合长期写作的博客。
published: 2026-11-05
category: Web 工程
tags: [Astro, 内容设计]
draft: false
```

分类适合回答「这篇文章大致在讲什么」，标签适合描述横向关联，系列则为需要顺序阅读的内容提供明确路线。三者各有用途，不必把它们合并成一个复杂的目录系统。

<Callout title="先写清楚，再考虑扩展">
  内容模型只记录真正参与页面展示与检索的信息。没有使用场景的字段，等需要时再添加。
</Callout>

## 把构建过程留在发布之前

静态页面把正文渲染、代码高亮、图片处理等工作放在构建阶段。读者打开页面时，浏览器先收到完整内容，只为真正需要交互的部分加载脚本。

对于个人博客，这种流程把日常维护压缩到两个动作：写内容，以及发布构建产物。正文不依赖一个持续运行的业务服务，迁移托管环境时也更直接。

### 什么需要 JavaScript

文章、导航、项目介绍都能直接阅读。只有搜索、收藏、工具和演示等交互才需要脚本。将边界画清楚，比盲目追求「零 JavaScript」更有帮助。

| 页面区域 | 首次展示   | 交互加载       | 主要职责       |
| -------- | ---------- | -------------- | -------------- |
| 文章正文 | 静态 HTML  | 无需           | 让内容尽早可读 |
| 全站搜索 | 搜索入口   | 按需加载索引   | 找到相关内容   |
| 工具箱   | 表单与说明 | React island   | 在本地转换输入 |
| 评论     | 状态提示   | 进入区域后加载 | 与读者讨论     |

## 建立可预期的写作流程

一篇新手记可以先作为草稿保存在仓库里。本地开发环境允许预览，正式构建统一过滤草稿。过滤逻辑应该放在内容查询入口，让列表、详情、系列和订阅使用同一份结果。

```ts
const articles = await getCollection('articles', ({ data }) => {
  return import.meta.env.DEV || !data.draft;
});
```

发布之前，检查摘要是否说明了文章的价值，图片是否有替代文字，以及示例代码是否能独立理解。技术正确性和阅读节奏都需要照顾。

### 写给未来的自己

记录一次决策时，除了「做了什么」，也保留当时的约束。未来回看，约束往往比结论更值得参考。把推理写清楚，会让文章成为可以继续修订的工作笔记。

> 不是每一篇手记都要回答大问题。有时，把一个小问题解释清楚，就已经足够。

## 为后续生长留出空间

保持源码、内容和构建产物的职责清楚。内容与图片放在一起，站点信息集中维护，页面通过组件组合扩展。这些简单的约定，比提前搭建插件系统更适合当前阶段。

下次想增加一个功能时，先问它能帮助读者完成什么，再决定是否值得实现。让需求推动结构的变化，让简单成为可以持续维护的结果。
